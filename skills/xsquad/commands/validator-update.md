# /xSq-validator-update — keep the validator suite honest

Validators rot the moment the app changes. This command is the upkeep loop for the suite
generated by `/xSq-validator-setup`: it re-grounds every validator against current source,
re-proves features live, and ships proven corrections. The unit of rigor is the feature,
not every sentence: cover every validator from source and exercise every feature live,
without terminalising every bullet.

It also has a **mid-run variant** the orchestrator uses during squad runs.

## Outcomes

Pick one, and say which:

- **clean** — every validator got source and live coverage; nothing worth shipping.
- **changed** — proven spec, script, or index corrections shipped.
- **blocked** — coverage could not finish or a proven fix could not ship safely. Say
  exactly what blocked it.

## Edit scope

Only edit `.xsquad/validators/` (specs, scripts, index). Never edit product code during a
run: a behavior the spec describes that the app no longer has is either doc drift (fix the
spec) or a product regression (report it, don't paper over it in the spec).

## Full pass

0. **Locate the target.** Read `.xsquad/validators/README.md` and glob sibling specs.
   None → stop and point at `/xSq-validator-setup`. Several projects' suites mixed →
   ask which.

1. **Index hygiene.** Fix missing, extra, duplicate, or dead entries in the index.
   Lightweight; no generated inventory.

2. **Source wave.** One read-only subagent per feature validator, launched concurrently.
   Each explains "how does this user-facing feature work?" from source, flags likely spec
   drift with citations, and returns one concise live-verification recipe. Children never
   drive the app and never edit files. Return shape: feature summary / source entry
   points / likely drift or none / one recipe.

3. **Reconcile.** Every validator now has a returned summary. Merge overlapping recipes
   into as few app states as practical. Spot-check cited drift; don't re-prove clean
   claims. Sweep recent churn (recent commits, new routes/commands) for user-facing
   surfaces missing from the suite — require a concrete source path before calling one
   missing, then write a new spec for it and prove it (step 4) before marking it proven.

4. **Live pass.** Required even when source looks clean. Drive every feature per the
   `/xSq-validator-run` procedure and hold its three invariants the whole pass. A
   feature that can't be reached is `verified-unreachable` only with the concrete
   prerequisite (auth, entitlement, OS, external state) and the route attempted; if the
   spec omits that prerequisite, that's drift. Any harness fix from triage gets re-driven
   live before it ships. Final teardown happens after the last drive.

5. **Triage.** When the findings stack up, bucket them first with the classifier pre-pass
   (`references/classifier.md`: `spec drift, harness gap, product gap, unclear`) and read
   only what falls below the confidence bar. Then: wrong or missing user-POV description
   → doc drift, fix it. Working behavior the harness can't drive → harness gap, fix it
   (scripts executable, invocation documented in the spec). App behavior that's actually
   broken → product gap; record it for the user, keep it out of this pass.

6. **Ship.** For changed: apply the corrections, re-read every changed file before
   declaring done, update the index (`proven <date>`), and append durable lessons to
   `.xsquad/MEMORY.md`. For clean or blocked: report the outcome and coverage honestly.

## Mid-run variant (orchestrator, inside a squad run)

Full passes are too heavy mid-task. After any task changes behavior:

1. List the validators covering the changed surface (their index line names it).
2. Re-read each affected spec against the new source; update **What it proves / Drive /
   Pass criteria / Gotchas** and any helper script — keep the user-POV behavior as the
   anchor, not the subagent's implementation details.
3. Re-prove each touched validator once (launch → doctor → drive → evidence → cleanup).
4. Update the index line (`proven <date>`) and, if a new behavior needs coverage the
   suite lacks, write a fresh spec for it and prove it before marking the task green.
5. Never weaken pass criteria to accommodate a subagent's shortcuts. If the behavior
   itself regressed, that's a product bug: fix brief, not spec edit.

Keep concise run notes (coverage, unreachable prerequisites, confirmed drift, outcome) in
the run directory; don't commit them.
